# 电子发票 PDF 交付与经营数据中心设计

## 文档定位

本设计覆盖两个已确认的阶段性改造：

1. 将管理员“完成电子发票”从手填发票号码、文件地址和邮件发送结果，调整为上传 PDF、预览、二次确认和小程序内领取。
2. 将当前“小程序业务账”重组为管理员专属的“经营数据中心”，明确区分财务资金、门票核销票数和实际入园人数。

本设计是下列旧文档相关章节的最新口径：

- `docs/plans/2026-07-28-invoice-request-design.md` 中“员工完成开票、邮件交付、交付字段”章节；
- `docs/plans/2026-07-28-admin-operations-ledger-design.md` 中“两层信息架构、一张票计一人、页面设计”章节。

旧版字段与页面保留兼容，但新增开发与验收以本文为准。

## 目标与非目标

### 目标

- 管理员通过选择 PDF 文件完成电子发票交付，不再手工粘贴 URL。
- 上传成功后先预览和确认，再将申请状态改为“已开票”。
- 申请人可在小程序内查看或下载电子发票。
- 管理员可从统一入口查看财务对账和门票核销数据。
- 财务对账支持日、月、自定义周期、账单统计、资金明细和订单下钻。
- 核销数据支持今日、历史日期、月度和自定义周期，并同时统计核销票数与实际人数。
- 双人票按“一张票、两个人”统计，票面金额与当天收入严格分离。
- 保留会员核销、长河令兑换等现有运营明细，不删除现有功能。

### 非目标

- 不接入第三方自动开票平台。
- 不自动发送电子邮件。
- 不建设 Web 管理后台。
- 不模拟微信支付商户平台手续费、分账、提现或银行卡结算状态。
- 不将核销票面金额当作收入。
- 不在第一阶段提供任意文件格式；只支持 PDF。
- 不承诺原生微信小程序支持操作系统文件拖放。

## 信息架构

### 员工模式

```text
员工模式
├─ 现场作业
│  ├─ 门票核销
│  ├─ 会员核销
│  └─ 长河令兑换
├─ 经营数据（仅管理员）
│  ├─ 财务对账
│  │  ├─ 今日概览
│  │  ├─ 账单对账（日 / 月 / 自定义）
│  │  ├─ 账单详情
│  │  │  ├─ 账单统计
│  │  │  └─ 账单明细
│  │  └─ 订单详情
│  ├─ 核销数据
│  │  ├─ 今日验证
│  │  ├─ 历史日期查询
│  │  ├─ 验证统计 / 按票种统计
│  │  ├─ 验证明细
│  │  └─ 订单详情
│  └─ 其他履约数据
│     ├─ 会员核销记录
│     └─ 长河令兑换记录
└─ 客户服务（仅管理员）
   └─ 开票处理
      └─ 上传 PDF → 预览 → 确认完成
```

### 页面职责

#### 经营数据首页

默认展示今天，提供四个核心指标：

- 今日实收金额；
- 今日实际退款；
- 今日支付订单；
- 今日实际入园人数。

主入口为“财务对账”和“核销数据”。会员核销与长河令兑换保留为次级入口，继续复用已有业务明细能力。

#### 财务对账

财务对账首页展示今日资金概览和风险；“查看全部账单”进入账单对账列表；选择某个周期进入账单详情。

账单详情分为：

- 账单统计：商品、订单类型、支付、退款、异常构成；
- 账单明细：逐笔支付、实际退款和补差价记录。

任何明细可进入统一订单详情。

#### 核销数据

默认展示今天，支持指定日期、月度和自定义范围。页面分为：

- 验证统计：核销票数、实际人数、关联订单数、票面金额、按票种构成；
- 验证明细：核销时间、票种、票号、人数、票面金额、订单号和核销员工。

任何核销明细可进入统一订单详情。

#### 订单详情

财务和核销共用一个管理员订单详情页，分区展示：

- 订单基本信息；
- 商品、数量和人数；
- 支付记录；
- 退款申请与实际退款；
- 门票及核销记录；
- 开票申请与电子发票；
- 异常和操作历史。

## 电子发票 PDF 交付

### 管理员流程

```text
submitted
  ↓ 开始审核
reviewing
  ↓ 选择 PDF
本地校验
  ↓
上传云存储
  ↓
服务端校验并绑定申请
  ↓
显示文件名 / 大小 / 上传时间 / 预览
  ├─ 重新上传
  └─ 确认完成开票
        ↓
      issued
```

管理员处理页调整如下：

- 删除发票号码输入；
- 删除文件地址输入；
- 删除“已发送邮件”勾选；
- 增加 PDF 上传区；
- 上传成功后显示文件摘要、预览和重新上传；
- 只有管理员点击“确认完成开票”后才进入 `issued`。

确认前允许替换文件。确认后不允许直接覆盖；如未来需要更正发票，应新增保留版本历史的“更正发票”流程，不能静默替换。

### 用户流程

申请为 `issued` 时展示：

- 发票状态；
- 对应订单和开票金额；
- PDF 文件名和开具时间；
- “查看电子发票”；
- “下载电子发票”。

用户从小程序获取短期可访问地址后下载并使用微信文档预览。邮箱仍可作为申请资料保留，但不再是完成开票的必需条件，也不显示“已发送邮件”承诺。

### 文件约束

- 仅允许一个 PDF；
- 最大 10MB；
- 客户端校验扩展名、大小和 `%PDF-` 文件头；
- 云函数再次下载并校验文件大小、文件头和存储路径；
- 存储路径包含申请编号和随机文件名；
- 数据库保存 CloudBase `fileId`、文件名、大小、上传时间、上传管理员和版本；
- 不保存永久公开 URL；
- 只有申请人和管理员可请求临时访问地址；
- 文件上传、替换、预览、下载和确认写入审计记录。

移动端正式交互为“点击选择 PDF”。上传区可以使用拖放框视觉，但不承诺操作系统文件拖入能力。

### 建议数据结构

`invoice_requests` 新增：

```js
invoiceFile: {
  fileId: String,
  fileName: String,
  size: Number,
  contentType: 'application/pdf',
  version: Number,
  uploadedAt: Date,
  uploadedBy: String,
  uploadedByName: String
}
```

旧字段 `invoiceNo`、`invoiceUrl`、`emailSent` 标记为兼容字段。新申请不再要求或写入这些字段；读取旧申请时仍可展示旧文件入口。

### 服务动作

`invoiceService` 增加：

- `attachInvoiceFile`：管理员绑定并校验已上传 PDF；
- `getInvoiceFileAccess`：申请人或管理员获取短期访问地址并写审计；
- 既有 `updateStaff(status=issued)`：改为必须存在有效 `invoiceFile` 和匹配 `revision`；
- 可选 `detachInvoiceFile`：仅 `reviewing` 状态下移除待确认文件。

状态迁移保持不变：`reviewing → issued`，但完成条件由旧三字段改为有效 PDF。

## 数据口径

### 财务

- 支付收入按 `orders.paidAt` 落入查询范围；
- 实际退款按票券或会员的 `refundedAt` 落入查询范围；
- 净收入 = 支付收入 − 实际退款；
- 待审核、处理中退款只作为风险，不提前扣减；
- `paid_dup` 计入已支付金额，同时计入异常；
- 补差价订单计入支付收入并单独标识；
- 开票申请不改变收入；
- 数据库存储整数分，页面显示元。

“账单对账”代表小程序内部业务账，不代表微信商户平台结算账。

### 门票与实际人数

一张票券记录始终计为一张核销票。实际人数来自该票券购买时保存的 `admissionCount`：

- 单人票、儿童票、老人票：1；
- 双人票：2；
- 后续多人票：使用商品配置的正整数。

同一周期分别展示：

- `verifiedTicketCount`：核销票数；
- `admittedPeopleCount`：已确认实际人数；
- `unknownAdmissionTicketCount`：人数待核对的历史票数；
- `relatedOrderCount`：去重订单数；
- `ticketFaceValue`：票面金额。

票面金额只表示已履约产品规模，不等于当天收入。

### 人数快照与兼容

`ticket_products` 增加 `admissionCount`；创建订单和出票时将人数快照写入订单及票券，核销记录再次保存该值。

历史推断顺序：

1. 使用票券明确的 `admissionCount`；
2. 使用已知 SKU 的版本化映射；
3. 已知单人 SKU 按 1；
4. 无法判断时不计入“已确认实际人数”，计入“人数待核对”。

不能仅根据商品名称中的自然语言静默猜测历史人数。

### 核销事实

- 新门票的事实来源为 `tickets.status=used + tickets.usedAt`；
- `verifications` 保存操作审计快照；
- 同一票号重复扫码不重复增加票数或人数；
- 重复扫码尝试写入审计；
- 已核销后退款、缺少订单、缺少人数、缺少票价均进入异常提示。

### 时间

- 所有查询使用 `[from, to)`；
- 页面按北京时间生成自然日和自然月；
- 日、月、自定义查询最大 366 天；
- 财务按资金发生时间，核销按 `usedAt`，两者不要求相等。

## 权限与隐私

- 经营数据、订单详情和开票处理仅 `status=approved && role=admin` 可访问；
- 普通员工继续使用现场核销、会员核销和长河令兑换，不显示经营金额和电子发票；
- 每个云函数都重新查询管理员身份，不信任前端状态；
- 申请人只能读取自己的发票文件；
- 电话在经营明细中只返回后四位；
- 客户 openid 不返回页面或 CSV；
- 敏感集合不允许小程序端直接读写。

## 页面状态与异常

所有新页面统一包含：

- 骨架加载；
- 空数据；
- 加载失败与重试；
- 无权限；
- 日期错误；
- 历史字段缺失；
- 查询截断；
- 列表分页；
- 防重复提交；
- 数据更新时间。

用户界面不直接展示 `-504002` 等基础设施错误码；云函数返回稳定业务消息，原始错误只记录日志。

经营数据异常至少包括：

- 已核销后退款；
- 门票人数待核对；
- 门票票面金额缺失；
- 核销记录缺少关联订单；
- 重复核销尝试；
- `paid_dup`；
- 长时间未处理退款；
- 开票文件已上传但未确认。

异常中心第一阶段只读，不自动修改业务事实。

## 视觉与交互

- 延续现有米白、墨绿和低对比阴影；
- 资金主数字与履约人数分卡展示；
- 金额使用人民币符号，人数使用“人”，票数使用“张”；
- 统计页不使用装饰性图表替代精确数字；
- 日期筛选默认今天，切换后自动刷新；
- 明细整卡可点击，进入订单详情；
- 所有触控区域不小于 `88rpx`；
- 页面一次只改一个，每页完成后生成自测清单。

## 验收标准

### 电子发票

- 管理员不能通过手填 URL 或号码完成新申请；
- 非 PDF、超过 10MB、伪造 PDF 文件头均被拒绝；
- 上传成功但未确认时仍为 `reviewing`；
- 管理员可预览和替换待确认文件；
- 确认后状态为 `issued`，普通员工不能覆盖文件；
- 申请人可查看和下载自己的 PDF，不能访问他人文件；
- 旧 `invoiceUrl` 申请仍可兼容展示；
- 退款冲突规则保持不变。

### 经营数据

- 普通员工看不到经营数据入口，直接调用也返回 403；
- 财务支持日、月、自定义周期和历史账单下钻；
- 核销支持今日、历史日期、月度和自定义查询；
- 双人票显示 1 张、2 人；
- 无法判断人数的历史票明确显示待核对；
- 票面金额不计入财务收入；
- 账单统计、账单明细和验证明细可进入统一订单详情；
- 会员核销和长河令兑换现有能力不丢失；
- 金额、时区、权限、分页和脱敏测试通过。

## 风险与控制

- CloudBase 文件上传成功但业务绑定失败可能产生孤儿文件；通过申请目录、替换清理和定时清理策略处理。
- 大范围查询可能触及云函数时间限制；限制 366 天、分页读取并展示截断提示。
- 旧票没有人数快照；必须展示待核对数量，不能伪造精确总人数。
- 支付、退款和核销可能发生在不同日期，财务金额与核销票面金额不一致是正常现象。
- 已开票文件具有业务敏感性；完成后不可静默覆盖，临时访问地址必须短期有效。
