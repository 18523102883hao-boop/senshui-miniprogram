# 已完成订单申请开票设计

## 目标

为正常支付完成的会员卡、门票和补差价订单补齐电子普通发票申请能力，并在现有员工模式内形成“游客提交—管理员审核—线下开票—邮件送达—游客查看”的闭环。

本期不接入航信、百旺等第三方自动开票平台。工作人员在线下开票系统完成开具和邮件发送后，再回到小程序登记结果。

## 已确认业务规则

1. 正常支付完成且仍有可开票金额的会员卡、门票和补差价订单可以申请开票。
2. `paid_dup` 重复支付异常订单、退款中、已退款订单不可申请。
3. 每个订单同一时间只能有一个有效开票申请，重复提交必须幂等。
4. 开票时效统一提示“预计在申请提交后 10 个自然日内完成审核并开具”，不显示实时倒计时。
5. 未开票时申请退款：允许继续退款，并自动关闭开票申请。
6. 已开票时申请退款：暂停自助退款，提示联系工作人员先处理红字发票。
7. 被驳回的申请可修改资料并重新提交；因退款关闭的申请只有订单仍有剩余可开票金额时才能重新提交。
8. 开票管理仅对已审批的 `admin` 员工开放。

## 用户流程

### 订单入口

“我的订单”的已完成订单按状态展示以下动作：

- 未申请：`申请开票`
- 已提交、审核中：`查看开票进度`
- 已开票：`查看发票`
- 已驳回：`修改并重新申请`

入口只负责导航，最终资格和金额均由云函数重新校验。

### 申请表单

页面首先展示不可编辑的订单名称、订单号和可开票金额。表单字段为：

- 发票类型：电子普通发票，固定值
- 发票内容：商品明细，固定值
- 抬头类型：个人 / 单位
- 抬头名称：必填
- 单位税号：单位抬头必填
- 接收邮箱：必填
- 注册地址、注册电话、开户银行、银行账号：单位抬头选填，默认折叠

切换为个人抬头时不提交单位专属字段。提交前展示订单号、金额、抬头和邮箱二次确认，避免把发票发往错误地址。

### 进度与结果

进度页使用三段状态：

`申请提交 → 商家审核 → 商家开票`

同时展示发票类型、发票内容、抬头、申请时间、当前说明和状态历史。完成开票后增加发票号码、邮件发送状态及发票文件入口；驳回时展示原因和重新申请入口。

## 员工流程

员工模式新增“开票管理”，仅 `admin` 可见。列表提供待审核、审核中、已开票、已驳回四个筛选项，并显示待处理数量。

管理员可以：

1. 打开申请详情并核对订单快照与开票资料。
2. 将“已提交”改为“审核中”。
3. 填写发票号码、发票文件链接，确认已经发送至申请邮箱后标记“已开票”。
4. 填写明确原因后驳回。

每次状态变更记录操作员工、时间、原状态、目标状态和备注。已经开票或因退款关闭的申请不可再次编辑为处理中。

## 状态机

开票申请状态：

- `submitted`：申请已提交
- `reviewing`：商家审核中
- `issued`：已开票
- `rejected`：已驳回，可修改后重提
- `cancelled_refund`：因退款关闭

允许的迁移：

- `submitted → reviewing | rejected | cancelled_refund`
- `reviewing → issued | rejected | cancelled_refund`
- `rejected → submitted`

`issued` 和 `cancelled_refund` 为终态。订单存在部分退款、仍有剩余可开票金额时，可基于原申请开启新的修订版本，金额必须重新由服务端计算。

## 数据模型

新增 `invoice_requests` 集合：

- 身份：`_openid`
- 订单快照：`orderId`、`outTradeNo`、`orderType`、`orderTitle`
- 金额：`invoiceAmount`，单位为分，由服务端计算
- 固定内容：`invoiceType=electronic_normal`、`contentType=item_detail`
- 抬头：`titleType`、`titleName`、`taxNo`
- 单位选填资料：`registeredAddress`、`registeredPhone`、`bankName`、`bankAccount`
- 交付：`email`、`invoiceNo`、`invoiceUrl`、`emailSent`
- 流程：`status`、`revision`、`rejectReason`、`history`
- 时间：`submittedAt`、`reviewedAt`、`issuedAt`、`createdAt`、`updatedAt`

`orders` 冗余 `invoiceRequestId`、`invoiceStatus` 和 `invoiceRevision`，用于订单列表直接决定按钮状态；云函数仍以 `invoice_requests` 为开票事实来源。

## 服务端边界

- `_openid` 只取 `cloud.getWXContext().OPENID`。
- 根据用户身份和订单号查询订单，不接受客户端传入金额、订单类型或商品名称。
- 门票订单按未退款票券重新汇总剩余可开票金额；其他订单使用服务端订单实付金额。
- 单位税号、邮箱和选填单位资料在服务端再次校验长度与格式。
- 创建和重新提交采用订单号与修订版本幂等，快速重复点击返回同一申请。
- 员工列表和状态更新必须重新查询 `staff`，且仅允许 `status=approved`、`role=admin`。
- 用户详情只允许申请人读取；订单列表不返回税号、银行账号等完整敏感字段。

## 退款协同

`refundMember` 与 `requestTicketRefund` 在发起退款前检查开票状态：

- `issued`：返回业务冲突，不调用退款接口。
- `submitted` / `reviewing`：退款成功或人工退款申请成功后，原子式将申请改为 `cancelled_refund`，同步订单开票摘要。
- `rejected`：不阻止退款。

门票发生部分退款时保留订单支付态，并记录已退金额或从票券重算剩余金额，后续开票不得包含已退款部分。

## 隐私与展示

- 隐私政策补充发票抬头、税号、邮箱、注册地址、注册电话、开户银行和银行账号的收集目的、使用范围和保存说明。
- 银行账号、税号在非编辑态默认脱敏；只有申请人和管理员可访问完整数据。
- 集合权限继续设为“所有用户不可读写”，全部访问经云函数。
- 表单明确说明资料仅用于开具和交付本次发票。

## 视觉与交互

沿用项目米白、墨绿和朱砂 Design Token，不照搬参考图的红色：

- 订单信息使用低对比摘要卡，表单使用清晰分组与统一圆角。
- 个人 / 单位采用分段选择器。
- 单位选填资料默认收起，降低首次填写负担。
- 进度页以克制的三段时间线表达状态，驳回原因使用提示卡。
- 主要操作固定在底部安全区，所有触控区域不小于 `88rpx`。
- 提交和员工状态更新均有忙碌锁、防重复点击、失败提示和可重试状态。

## 风险与兼容

- 旧订单没有开票摘要字段时按“未申请”处理，但云函数仍需重新判断资格。
- 订单与开票申请跨集合更新可能部分失败，读取时以开票申请为准并允许服务端修复订单摘要。
- 邮件由工作人员线下发送，小程序不承诺自动邮件投递；管理员必须勾选已发送才能完成开票。
- 发票文件链接由管理员录入，页面需限制为 HTTPS 或受支持的云文件地址。
- 本期不处理红字发票流程，只阻断已开票订单的自助退款并引导人工处理。

## 验收标准

- 三类正常已支付订单可申请，异常和退款订单不可申请。
- 表单正确区分个人与单位必填项，服务端拒绝篡改金额和无效资料。
- 重复提交不产生重复申请。
- 用户可以看到提交、审核、开票和驳回状态。
- 管理员可以完成审核、开票和驳回，普通员工无法读取开票资料。
- 未开票退款自动关闭申请；已开票订单无法自助退款。
- 隐私政策、数据模型、数据库初始化和页面注册同步更新。
- 新增测试及项目全量测试通过。
