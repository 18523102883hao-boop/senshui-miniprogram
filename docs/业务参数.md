## 4. 退款规则

1. 未使用可**随时退款**。
2. 过期后未使用，商家审核后**自动退款**。
3. 本产品包含多项游玩服务，**任一项目核销后，未使用项目金额不可申请退款**。
4. 一次性购买多份时，支持未使用商品经商家审核后**部分退款**。

> 会员卡沿用既有规则（7 天内未核销可退），与门票规则相互独立。

## 7. 企业微信 / 客服二维码（位置已预留，待业主提供）

配置在 `miniprogram/env.js` 的 `qrcodes`，取用统一走 `utils/qrcode.js` 的 `getQrcode(scene)`。

| 场景键 | 用途 | 消费页面 |
|---|---|---|
| `concierge` | 通用园区管家 | 管家服务页；也是其余场景的**回落**目标 |
| `birthday` | 生日宴请顾问 | 服务详情页（type=birthday） |
| `teamBuilding` | 公司团建顾问 | 服务详情页（type=team_building） |
| `brand` | 品牌合作商务 | 服务详情页（type=brand） |
| `welfare` | 新客福利官 | 预留（首页新客福利） |
| `complaint` | 投诉建议专员 | 预留（投诉建议页） |

**填法**：图片传到云存储 → 复制 fileID（`cloud://` 开头）或 https 地址 → 填进对应字段。

**行为保证**（已被 9 个测试锁定）：
- 未配置的场景**整块不渲染**，不出现空白框或裂图 —— 所以可以一个一个陆续填；
- 专属码未配时**自动回落**到 `concierge` 通用码，并标注「由园区管家统一对接」；
- 只配 `concierge` 一个，六个场景就全部可用；后续再补专属码会自动覆盖。

```js
// env.js 示例
qrcodes: {
  concierge: 'cloud://cloud1-xxx/qr/concierge.png',
  birthday: '',      // 留空 = 回落到 concierge
  teamBuilding: '',
  brand: '',
  welfare: '',
  complaint: ''
}
```

## 8. 产品策略：企微直连优先（业主 2026-07-25 决策）

> 「很多功能只需要把企业微信二维码和预约电话给出来即可，让客户添加后与工作人员详细联系，
> 更高效准确，而不是让客人自己去填各种信息。」

因此以下场景**主行动改为「加企微 + 打电话」**，自助表单退为次要入口（能力保留，不删）：

| 场景 | 主行动 | 次要入口 |
|---|---|---|
| 团队预约（`reservation/entry`）| 加管家微信 / 致电 | 自助提交预约需求、我的预约 |
| 生日宴请 / 公司团建 / 品牌合作（`service/detail`）| 加顾问微信 / 致电 | 「不方便加微信？填写需求表单」 |
| 管家服务（`concierge`）| 加管家微信 / 致电 | 微信客服、咨询表单 |

**为什么保留表单**：部分客户不愿加微信，或在非工作时间想先留个信息。删掉等于堵死一条路。
主次调换即可，代价为零。

**健壮性**（测试锁定）：
- 二维码未配置 → 整块不渲染，只显示电话
- 二维码配了但图片加载失败（404）→ **自动隐藏，只留电话**，绝不留裂图
- 电话始终可用，是任何情况下的兜底与无障碍替代路径

## 10. 营地与溪降营业时间必须分别标注

业主 2026-07-25 指出：**营地开到 18:00，溪降 16:30 就结束**，只写一个时间会让客人以为整个园区都是那个时段。

| 项目 | 时间 | 中途节点 | 配置位置 |
|---|---|---|---|
| 营地 | 10:00–21:00 | **19:00 停止供餐** | `env.js` → `park.hours.camp` |
| 溪降 | 10:00–16:30 | 16:30 是**停止检票**，不是清场 | `env.js` → `park.hours.creek` |

计算逻辑在 `utils/park-status.js`，首页与园区 Tab 共用，三种状态：

| 状态 | 含义 | 视觉 |
|---|---|---|
| `open` | 正常营业 | 绿色 |
| `partial` | **仍营业但中途服务已停**（营地过 19:00 点不了餐）| 金色 |
| `ended` | 当日结束 | 灰色 |

典型场景（测试锁定）：
- **17:00**：营地进行中 / 溪降已结束
- **20:00**：营地「已停止供餐」（金色，仍可停留）/ 溪降已结束

`partial` 这档很重要——否则 20:00 到园的客人会以为还能点餐。

## 11. 二级页面常驻底部导航

业主 2026-07-25：「在补差价页面看不到 Tab，只能点左上角返回」。

**平台限制**：微信的 tabBar（含自定义）只在 `app.json` 的 `tabBar.list` 声明的 4 个页面显示，
`navigateTo` 打开的页面不显示——这是机制，无法通过配置改变。

**解决**：`sr-tabbar` 组件在浏览类二级页面手动渲染同款导航，点击走 `switchTab`。

| 类型 | 是否加 | 页面数 | 理由 |
|---|---|---|---|
| 浏览类（说明/目录/列表/详情）| ✅ | 22 | 看完能直接切换，少一次返回 |
| 任务流（下单/支付/退款/表单）| ❌ | 6 | 误点会中断流程、丢失已填内容 |
| 员工端 | ❌ | 8 | 与游客 Tab 无关 |

同时有底部操作栏的页面（门票详情、服务详情），操作栏已上移避免与导航重叠。

## 11. 溪降调价（2026-07-26）与补差价联动

业主 2026-07-26 调整溪降票价，儿童溪降与营地票价不变：

| 票种 | 原价 | 现价 |
|---|---|---|
| 单人溪降 | ¥58 | **¥68** |
| 双人溪降 | ¥88（人均 44） | **¥128**（人均 64） |
| 儿童溪降 | ¥29.9 | 不变 |
| 营地各票 / 套票 | — | 不变（套票仍 ¥178） |

**补差价必须跟着改**，因为定价存在一条不变量：

```
单项票价 + 升级差价 = 对应套票价（成人 178）
```

只涨溪降不动差价，客人先买溪降（68）再升级（120）要花 188，比直接买套票 178 还贵。
因此同步下调：

| 升级项 | 原差价 | 现差价 | 依据 |
|---|---|---|---|
| 成人单溪降 → 升营地 | ¥120 | **¥110** | 68 + 110 = 178 |
| 双人单溪降 → 升营地（每人） | ¥134 | **¥114** | 64 + 114 = 178 |
| 亲子单营地 → 升溪降（大人） | ¥58 | **¥68** | 等于单人溪降票价 |
| 成人单营地 → 升溪降 | ¥20 | 不变 | 158 + 20 = 178，与溪降价无关 |
| 儿童相关三项 | — | 不变 | 儿童溪降价未调 |

价格散在四处，改一处漏三处很容易发生：

| 位置 | 作用 |
|---|---|
| `cloudfunctions/seedTicketProducts/seed-tickets.js` | 票种种子 |
| `cloudfunctions/seedUpgradeItems/index.js` | 升级项种子 |
| `miniprogram/pages/upgrade-info/upgrade-info.js` | 补差价页展示文案（硬编码） |
| 云端 `ticket_products` 集合 / `notices.upgradeList` | **线上实际生效的值** |

`tests/feature-expansion/pricing-consistency.test.js` 锁死了上述不变量与三处本地配置的一致性，
但**云端数据库不在测试覆盖范围内**——改价后必须重新执行种子函数，否则线上仍是旧价。
